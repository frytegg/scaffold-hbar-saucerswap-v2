# Hedera-specific behaviour, handled and tested

Eight things that standard Ethereum tooling reports wrongly, or not at all, on Hedera. All of them were executed on Hedera testnet, from a browser wallet, from research scripts and from this template's own commands; every transaction below can be opened on the mirror node, which answers machine-readable JSON, and on Hashscan, which renders it for a person.

Each section says what a developer sees, what the network really does, which transactions prove it, what the mistake costs in HBAR, which code protects against it and which test keeps that code honest.

Versions everything below was observed on: Hedera testnet (chain 296), the hashio JSON-RPC relay at version relay/0.78.5, viem 2.39.0, MetaMask 13.48.0 on Chrome 152, 21 to 23 September 2026. These are dated observations of one network, not rules of Hedera: the keyless checks of `yarn check:live` re-assert them, and fail the day they stop being true.

## HBAR has two units, and the wrong one fails under another name

**Symptom** — a swap that pays HBAR carries its amount twice: once in the calldata, as the `amountIn` the router is told to spend, and once in the transaction's `value`. Write the same figure in both, which is what an Ethereum habit produces, and a default viem or wagmi flow dies before it sends anything: `simulateContract` and `estimateContractGas` answer `CONTRACT_REVERT_EXECUTED, INSUFFICIENT_TOKEN_BALANCE`. Nothing was sent, nothing was charged, and the message is about a token balance for a mistake about HBAR. A caller that supplies its own gas limit skips the estimate and meets a different refusal, from the relay, which does name the unit: `-32602`, "Value can't be non-zero and less than 10_000_000_000 wei which is 1 tinybar". Between the two sits the case that says nothing at all: a value that is not a whole number of tinybar is accepted, the transaction succeeds, and the remainder is gone.

**Real cause** — inside the EVM every HBAR amount is tinybar, 10^8 to the HBAR: `msg.value`, `address(this).balance`, a calldata amount, and every amount the mirror node reports. A JSON-RPC transaction's `value` is not. It is weibar, 10^18 to the HBAR, the unit an Ethereum tool expects, and the relay divides it by 10^10 before the transaction reaches consensus. One HBAR is therefore `1000000000000000000` in the signed transaction and `100000000` everywhere else. Passing the calldata figure as the value sends 10^10 times too little, so the router finds no HBAR to wrap, tries to pull wrapped HBAR tokens from the sender instead, has none to pull, and the token service answers 178, `INSUFFICIENT_TOKEN_BALANCE`: a true answer to the question the router asked and the wrong one for the developer. The relay's own precheck, the one that names tinybar, runs at `eth_sendRawTransaction`, which a default flow never reaches. And the division is a truncation rather than a check: a remainder below 1 tinybar is dropped, while the relay keeps reporting the value that was signed, so `eth_getTransactionByHash` is not what moved — the mirror node's `amount` is.

The scope of the last row is worth stating exactly: a transaction the relay refuses never reaches consensus, so there is no hash to open and no fee to report. Two agents of this project recorded that answer in their own JSON-RPC traces, on viem 2.56.8 and on the 2.39.0 this template pins, and the sentence also exists in the relay's source; nobody has re-derived it from the chain, because there is nothing on the chain to derive it from.

**What it costs** — the two refusals cost nothing but the time spent reading about a token balance that was never the problem, which is the whole point of the trap: the cheap mistake is the one reported under another name. The case that is not a refusal costs HBAR quietly. A value with a sub-tinybar remainder is carried, charged in full and silently reduced, and no receipt, wallet or explorer marks the difference between what was signed and what moved: the transfer above was signed for 10,000,000,001 weibar, delivered 1 tinybar, and paid **0.02289 HBAR** to do it — its 21,000 gas at 109 tinybar per gas, the gas being the one in `packages/nextjs/lib/hedera/__tests__/fixtures/mirror/result-sub-tinybar-remainder.json`. The correct path costs exactly that and not a tinybar less: a whole-tinybar value of the same size is the same 21,000 gas and the same fee, so the price is not where the mistake shows, and what it buys is a remainder that went nowhere.

**How the template protects** — `packages/nextjs/lib/hedera/units.ts` makes the two units two types. `Tinybar` and `Weibar` are branded bigints; `tinybar` and `hbarToTinybar` build the first, `toWeibar` is the only way to the second, and the way back, `toTinybar`, is for a value read off the chain rather than for building a call. `payable` is the one function that produces a transaction value outside that module, and what it protects the send path with is its signature rather than a check inside it: it takes a `Tinybar` and returns the weibar, so the unscaled figure a developer would have written is not something a caller can hand to viem as a value at all. The check it runs on what it has just scaled, `assertJsonRpcValue`, refuses a non-zero value below 10^10 weibar and a value that is not a whole number of tinybar, quoting what the network would drop — but a scaled tinybar is neither of those, so the branch that fires in practice is the one on the way back: `toTinybar` runs the same check on a value read off the chain, which is where a sub-tinybar remainder is named rather than rounded away. Given the `amountIn` the call spends, `payable` refuses a value that does not cover it with the sentence "Transaction values are weibar: pass amountIn × 10^10"; the builders here do not pass that second argument, because each gives `payable` the same amount it wrote into the calldata, and `valueShortfall` is the same comparison without the throw. `explainError` in `packages/nextjs/lib/hedera/failure.ts` covers the case where they are met anyway: told the call's `value` and `amountIn`, it answers the misleading `INSUFFICIENT_TOKEN_BALANCE` as `unscaled-value` with the action `scale-value`, and it leaves the same status alone when the value does cover the amount, because then it really is a balance. A lint rule closes the door: `packages/nextjs/eslint.config.mjs` fails on a `value:` written in the object passed to a viem action or wagmi hook that sends, simulates, estimates, prepares or deploys, on a `value:` in a request object built before such a call, on `parseUnits(amount, 18)`, and on importing `parseEther` or `formatEther`, everywhere outside `packages/nextjs/lib/hedera`. In Solidity, `packages/hardhat/contracts/SaucerSwapHbarConsumer.sol` takes its amount in tinybar and reverts with `ValueBelowAmountIn` when `msg.value` is under it, which is what a caller that scaled the calldata instead of the value would produce.

**The test that keeps it fixed** — `yarn test:unit`: "the consumer's swap: the relay echoes the weibar signed, the mirror records the tinybar moved" and "msg.value reached the contract as those 6000000 tinybar: it gave back what they exceeded amountIn by" hold the two units against this template's own transaction, and "a value that is not a whole tinybar succeeds and loses the remainder, so the guard refuses it first" holds the truncation against the transfer above. "refuses 10^8 weibar, the unscaled value of 1 HBAR, as below one tinybar" and "refuses a value in tinybar where weibar is due" are the guards themselves. On the error path, "an unscaled value reads as INSUFFICIENT_TOKEN_BALANCE, which alone would advise funding the account" is the misleading answer, "with the call's value and amountIn, the same answer is explained as the unit mistake it is" is the correction, and "RespCode(178) on a direct call with a correct value stays a balance problem" is the control that keeps the correction from spreading; "the relay's -32602 value precheck at send time: scale the value, quoting the relay" and "finds the -32602 value precheck inside a bare HttpRequestError whose shortMessage says nothing" replay the relay's own sentence through the pinned viem, and "a -32602 for another reason is not a unit mistake: the relay's sentence is shown, with no advice" keeps that one narrow too. The lint rule has its own tests against a file of planted violations: "fails a planted value: and the ether helpers in hooks/, and nothing else", "sees a value set on a request object built before the call, asserted or not" and "leaves a value that is an ordinary property of an object nothing sends". The route is held by "carries the amount as weibar, ten orders of magnitude above the tinybar of the call" and "spends the token, not HBAR: the transaction carries no value". `yarn test:mock` holds the Solidity half: "refuses a value below the amount to swap, naming both in tinybar".

## The simulators approve a swap the network refuses

**Symptom** — a token-input swap on SaucerSwap V2 needs an HTS allowance for the router. With no allowance, `eth_call` answers a normal result, `eth_estimateGas` answers a number, and the mirror node's own simulator accepts the call as well. The wallet has nothing to warn about: it displayed a network fee of 1.0912 HBAR, a Confirm button and no warning of any kind. The transaction then failed on the network, and the wallet's own history shows "Interaction failed" with no reason at all.

**Real cause** — an allowance over an HTS token is held by the token service, below the EVM. A simulation runs EVM logic against ledger balances; the allowance is checked when the transaction reaches consensus, and the router's `exactInput` only then gets the response code 292, `SPENDER_DOES_NOT_HAVE_ALLOWANCE`, back from the token service at `0x167`. The simulators are not blind to the token service in general: a swap for more SAUCE than the sender holds is refused by all three (`INSUFFICIENT_TOKEN_BALANCE`), and `eth_call` refuses a swap whose recipient cannot receive the token (`TOKEN_NOT_ASSOCIATED_TO_ACCOUNT`), called directly and through the multicall — its two answers of 22 September 2026 are the fixtures `packages/nextjs/lib/hedera/__tests__/fixtures/rpc/call-direct-unassociated-184.json` and `packages/nextjs/lib/hedera/__tests__/fixtures/rpc/call-multicall-unassociated-184.json`, which the offline tests replay. What the other two answer for that recipient was not asked. The miss is the allowance check. One more layer hides the reason afterwards: SaucerSwap's router inherits Uniswap's `multicall`, which drops a revert shorter than 68 bytes, so the mirror node's `error_message` for the failed swap is `0x` and the response code survives only in the transaction's `/actions` view and in its child records.

**Proof** — four transactions of the same account, 0.0.10645914, on 21 and 22 September 2026:

**What it costs** — the failed swap burnt **0.13498778 HBAR** (123,842 gas at 109 tinybar per gas) and bought nothing: the pool had already paid out and called back before the router's own pull failed. The path that works cost **0.79222944 HBAR** for the approval and **0.98327156 HBAR** for the swap. The check that avoids the loss is one keyless read of `allowance(owner, router)`, which costs nothing and is answered in one round trip.

**How the template protects** — `allowanceVerdict` and `checkAllowance` in `packages/nextjs/lib/hedera/preflight.ts` read that allowance before anything is signed and refuse the send when it is below `amountIn` — `>=`, never `> 0`, because of the second transaction above. The verdict carries the action `approve` and a sentence naming the amount to approve. If a swap fails anyway, `explainError` and `postMortem` in `packages/nextjs/lib/hedera/failure.ts` fetch `/actions` when `error_message` is `0x`, decode the `RespCode` the `multicall` erased and answer one sentence with the same action.

**The test that keeps it fixed** — `yarn test:unit`: "the captured eth_call accepts a token -> HBAR swap with allowance 0, and the preflight refuses it" replays the captured simulator answer and the refusal, and "the token -> HBAR swap without allowance (0x756b…dabc): 0x on chain, RespCode(292) in /actions" replays the mirror node's answers for the script's own run of the same mistake. `yarn check:live` re-asserts, against the live network, that the three simulators still accept a swap with no allowance.

## A token cannot reach an account that has never held it, and who that actually bites

**Symptom** — a swap whose recipient is not the sender. The pool pays out, the transfer at the end is refused, the whole transaction reverts and the gas is charged. Called directly, `exactInput` comes back as `TransferFail(184)`, a custom error with a number in it and no words; wrapped in the `multicall` that a Uniswap ABI leads you to write, it comes back as nothing at all. A viem receipt says `reverted` either way, and nothing in the wallet, the receipt or the revert data names the recipient or the token.

**Real cause** — an account holds an HTS token only once a relation between the two exists, and the token service refuses a transfer to an account that has none. An account may also carry automatic association slots, which spend themselves on the first arrival of a new token: `-1` for unlimited, `0` for none, a positive number for a budget. This is where the received wisdom goes wrong, and where the honest version is more useful. Every entity this project has created through the JSON-RPC relay from an EVM key — the account this template's commands and the browser session both signed with, a fresh account made the morning of 23 September, and the contract this template deploys — was born with `-1`, and all three still answer it; three is the whole of that sample, so a newcomer with MetaMask swapping to themselves rarely meets this at all: the first SAUCE associates the account inside the swap, with no separate association transaction to send. It bites three other cases. A recipient that is not the sender, whose slots the sender cannot see without asking. An account with a finite budget, which the mirror node reports without saying how much of it is spent — and at the bottom of that range, SaucerSwap's own router 0.0.1414040 and position manager 0.0.1308184, created in 2024 outside the relay, carry none. And any contract meant to hold a token, not because it cannot be associated automatically but because somebody has to pay for the relation, and paying at deployment is not the same as paying inside every user's first swap. It is not a rule about fungible tokens either: the position NFT of a V2 liquidity position is an HTS token, so opening a position needs a slot or a relation exactly as a swap does.

The two refusals are captured for the offline tests, as answers and as records: `packages/nextjs/lib/hedera/__tests__/fixtures/rpc/call-direct-unassociated-184.json` and `packages/nextjs/lib/hedera/__tests__/fixtures/rpc/call-multicall-unassociated-184.json` are what `eth_call` answered for each shape, `packages/nextjs/lib/hedera/__tests__/fixtures/mirror/actions-multicall-unassociated-recipient-184.json` is where the erased reason survives, and `packages/nextjs/lib/hedera/__tests__/fixtures/mirror/transaction-direct-unassociated-recipient-184.json` and `packages/nextjs/lib/hedera/__tests__/fixtures/mirror/transaction-multicall-unassociated-recipient-184.json` are the two transfer lists. Three accounts are captured with them: `packages/nextjs/lib/hedera/__tests__/fixtures/mirror/account-unlimited-slots.json` for the unlimited case, `packages/nextjs/lib/hedera/__tests__/fixtures/mirror/account-zero-slots-unassociated.json` and `packages/nextjs/lib/hedera/__tests__/fixtures/mirror/account-zero-slots-associated.json` for the two shapes of no slots at all. The fourth case has no capture: this project has never met a testnet account with a finite non-zero budget, so the test for it edits one of those three into that shape and says so. What is a dated observation and not a rule is the `-1`: it is what this relay gave every account and every contract this project created in September 2026, on testnet, while the two SaucerSwap contracts created in 2024 outside it answer `0` to the same read. Whether a judge's own account, a wallet that creates accounts another way, or mainnet behave the same was not asked, so the pre-flight reads the recipient rather than assuming it.

**What it costs** — the refused transfer is charged like any other: **0.11455355 HBAR** for the direct call and **0.11738101 HBAR** for the multicall, each the gas used at 109 tinybar per gas, taken from the sender's own line in the two transaction records above. Nothing arrived: neither the recipient nor the router appears in either transfer list. The relation itself is bought once per account and per token and then costs nothing again, which is why this template's consumer buys it in its constructor rather than in its swaps — that deployment is the third transaction of "A failed HTS operation can be a successful transaction" below, and the swap that follows it carries no association step at all. Reading the recipient's account and its relation on the mirror node, which is what avoids the loss, is two keyless GETs and costs nothing.

**How the template protects** — `recipientVerdict` and `checkRecipient` in `packages/nextjs/lib/hedera/preflight.ts` ask the mirror node for the recipient's account and its relation with the token before anything is signed, and answer one of six things. `pass`, when the relation is already there. `pass` with `autoAssociates` set, when there is no relation and the slots are unlimited — which is also what tells the cost preview that this swap pays for an association. `warn` with the same flag, when there is no relation and the budget is finite, because the mirror node does not say how much of it is spent. `fail`, when there is no relation and no slot. `fail` with the action `fund` rather than `associate`, when no account exists at the address at all. And `fail` for the long-zero form of an account that has an EVM address of its own, which the network refuses as `INVALID_ALIAS_KEY` whatever its slots say. The two verdicts that are about the association carry the action `associate` and say the swap would revert and still charge the gas. `lpNftSlotVerdict`, inside `checkPositionMint` in `packages/nextjs/lib/hedera/positionPreflight.ts`, is the same check for the position NFT, named by its own token id. If the send happens anyway, `explainError` in `packages/nextjs/lib/hedera/failure.ts` turns `TOKEN_NOT_ASSOCIATED_TO_ACCOUNT` into one sentence with the action `associate`, and fetches `/actions` to find it when the `multicall` left `0x` behind. In Solidity, `packages/hardhat/contracts/SaucerSwapHbarConsumer.sol` associates itself with its output token in its constructor and refuses to exist if the token service answers anything but 22.

**The test that keeps it fixed** — `yarn test:unit`: "no slot and no relation blocks the send, and says why", "no slot but an explicit relation passes", "unlimited slots without a relation pass, and the swap will associate" and "limited slots without a relation warn: the mirror does not say how many are free" are the four answers about the association itself, the last of them against the edited account above. The other two are "an address with no account is refused" and "the long-zero form of an account with its own EVM address is refused, naming the address to use", whose control, "the long-zero form of an account without an EVM address of its own is its address, and passes", keeps that refusal from spreading to the accounts for which the long-zero form is the only address there is. The position NFT has its own three: "blocks an account with no slot and no relation, and names the token to associate", "passes an account with unlimited slots and warns about a limited one, which the mirror cannot count" and "passes an account that already holds positions of this collection". On the decoder, "direct call to a recipient without the token: TransferFail(184) means associate" and "the same through multicall: no revert data, the status name survives in the relay text only" replay what a simulator answers, while "the multicall to a recipient without the token (0x4d10…a483): TransferFail(184) in /actions" and "the direct call (0xc0fb…976b) keeps its revert data, so no /actions request is made" replay the mirror node's view of the two transactions above, the second one asserting that no `/actions` request is made when the reason is already there. "the two swaps refused for a missing association paid for their gas and delivered nothing" is the cost, read from their transfer lists. The route is held by "blocks the send when the recipient has no free association slot". `yarn test:mock` reproduces the failure itself against an original token service: "TransferFail(184) when the recipient has never held the token: the direct call keeps the reason" and "the same failure through multicall comes back with no data at all".

## Some calls cannot be priced, and the wallet then cannot send them

**Symptom** — opening a SaucerSwap V2 liquidity position is a `mint` on the position manager. Both `eth_call` and `eth_estimateGas` refuse it with `CONTRACT_REVERT_EXECUTED, INVALID_NFT_ID`, directly and through `multicall`, although the network executes the very same call. A wallet asks the relay for that estimate to price the transaction: MetaMask displayed "network fee unavailable" and the send failed. A dapp that lets the wallet estimate cannot open a position on Hedera today. Standard tooling reports this as an ordinary failure: before this template's decoder, the send came back as an empty revert with viem's "RPC endpoint returned HTTP client error", which tells a developer nothing.

**Real cause** — the mint reads the position NFT that the call itself is about to create, and the answer of that read outside a real transaction is `INVALID_NFT_ID`. That it is an artefact of the simulators, not a property of the call, was shown by replaying two mints that had succeeded at the block before their own: both simulators refuse the calldata they had just executed, while a swap and a `decreaseLiquidity` replay cleanly. It is not a general rule of the position manager either: a keyless simulation prices `increaseLiquidity`, and the wallet priced `decreaseLiquidity`, `collect` and `burn` itself in the same session, with no limit from the page. What was checked, how, and what was left out of the rules is recorded in `packages/nextjs/lib/hedera/gasRules.ts`.

The cost preview follows the same rule: `checkCost` in `packages/nextjs/lib/hedera/preflight.ts` estimates a call the relay prices and takes the rule's limit for a call it does not, says "up to" either way, and carries `WALLET_FEE_NOTE`, the sentence that explains why the wallet announces more.

```ts
import { type BuiltCall, gasRuleFor, withGasLimit } from "~~/lib/hedera";

/** The call, ready to send: the limit is explicit, and building it without one throws instead of failing in a wallet. */
export function readyToSend(call: BuiltCall): BuiltCall & { gas?: bigint } {
  const functions = ["mint", "refundETH"];
  return withGasLimit(call, { functions, gas: gasRuleFor(call.address, functions)?.gasLimit });
}
```

**The test that keeps it fixed** — `yarn test:unit`: "withGasLimit refuses to build a call nothing can price without one" checks the refusal, its code and the limit it names; "eth_call refuses the mint with INVALID_NFT_ID: the answer is that it cannot be priced" and "eth_estimateGas refuses it the same way" replay the captured answers through the pinned viem; "the wallet's own refusal, when it could not price the call, says the same thing" replays what the wallet gave back. Three controls keep the answer from spreading: "an empty revert through multicall stays an empty revert, with the mirror post-mortem to read"; "a mint that no simulator prices asks for a limit; a burn of a serial that does not exist does not"; and "the same sentence for a call a rule does not cover names the refusal instead of asking for a limit". "every rule's limit leaves room above every execution it records" and "counts the mint this template's own command sent, which is the largest of the three" keep the limits honest as executions are added.

## The wallet prices the gas limit; the network charges the gas used

**Symptom** — the fee a wallet shows before the signature is not the fee the account pays, and the gap is not small. Over the seven transactions of one browser session it was larger every single time: by about a tenth on the closest of them, and by eight times on a swap that then failed. A dapp that supplies a generous gas limit — which some calls on Hedera require, as the section above shows — makes that figure grow with the limit rather than with the work, and a user shown 2.85 HBAR for a transaction that will be charged 0.82781031 has no way to tell which of the two numbers is real.

**Real cause** — a wallet cannot know the gas a transaction will use before it runs, so it prices the only figure it has: the gas limit, at the gas price the relay answers. Two things then pull that apart from what the network takes. The limit is above the gas used by construction, and far above it when the dapp had to choose it with no estimate to size it from. The network's half of this is the good half — unused gas is not charged, which is what makes a generous limit safe — but the wallet cannot show it, and MetaMask 13.48.0 does not try. It does not even revise the limit it is handed: the two transactions below whose limit the page supplied reached the network carrying exactly that limit, which is why a number the dapp chose is what the user was asked to accept.

## A failed HTS operation can be a successful transaction

**Symptom** — a contract, or a wallet, asks the token service to associate an account with a token it already holds. The transaction succeeds: `status: 0x1`, viem's receipt says success, Hashscan shows a green tick, and the fee is charged in full. Nothing happened. The only trace of the refusal is the return value, `194`, and the child record the transaction left behind. A contract that calls the token service and does not read what it answered therefore records a success for an operation the network refused, and a UI that reads the receipt tells its user it worked. The same shape hides a missing association (`184`) and an insufficient balance (`178`).

**Real cause** — the Hedera Token Service is not an EVM contract. The system contract at `0x167` is a facade in front of the ledger, and the ledger answers with a response code from Hedera's own `response_code.proto` — 22 `SUCCESS`, 178 `INSUFFICIENT_TOKEN_BALANCE`, 184 `TOKEN_NOT_ASSOCIATED_TO_ACCOUNT`, 194 `TOKEN_ALREADY_ASSOCIATED_TO_ACCOUNT` — instead of reverting. From the EVM's point of view the call returned 32 bytes and returned them successfully, so the transaction is a success and is charged like one. The real status survives in two places the receipt does not show: the mirror node's `call_result` for the transaction, which is the response code, and the child record the transaction created, whose `result` names the status.

## Emptying a position pays a wrapped token, unless the call is split in three

**Symptom** — a SaucerSwap V2 position over an HBAR pool holds wrapped HBAR, and `collect` is the call that pays it out. The pattern a Uniswap reader writes first — one `collect` naming the manager as recipient for both tokens, then a sweep — reverts. The pattern SaucerSwap's own liquidity documentation shows — one `collect` to the user, then `unwrapWHBAR` — succeeds, and leaves the user holding WHBAR tokens instead of HBAR, with an unwrap that moved nothing. Neither failure says which of the two tokens was the problem.

**Real cause** — a `collect` is paid out by the pool, not by the manager, and every token movement on Hedera goes through the token service, which refuses to send a token to an account that has never held it. The position manager is associated with the wrapped HBAR and with the position NFT, and with nothing else, so asking it to receive the pool's other token is refused with `TOKEN_NOT_ASSOCIATED_TO_ACCOUNT` and comes back as the pool's `TransferFail(184)`. `unwrapWHBAR`, for its part, unwraps what the **manager** holds: run after the tokens have already left for the user, it has nothing to unwrap and succeeds without moving anything. The order that works asks for one token at a time: the wrapped HBAR into the manager, the unwrap that turns it into native HBAR for the user, then the other token straight to the user. That middle call is a sweep and not a transfer of a named amount: it sends the manager's **whole** wrapped-HBAR balance to the recipient, whoever left it there, and its `amountMinimum` argument is the only thing it checks. It is the shape `refundETH` has — in the mint of serial 359 above, `refundETH` returned this project more HBAR than the margin it had sent, because earlier callers had left theirs in the manager — so a collect can pay out more than the position was owed, and with a floor of zero a collect that pulled nothing at all succeeds and is charged in full.

The collect is the whole payout in one transaction and one signature, and its fee is more than eight times what the HBAR side of those positions was worth — a range this small is for proving the path, not for earning on it. The documented pattern leaves the user with a wrapped token, so the HBAR only arrives after a second transaction that this project has not measured. The Uniswap pattern costs whatever the reverted transaction's gas comes to and delivers nothing.

**How the template protects** — `buildSplitCollect` in `packages/nextjs/lib/hedera/position.ts` builds the three calls in that order and takes the recipient as its only address, so the other two patterns cannot be written by mistake. It also takes the floor the unwrap is given and refuses to build a collect whose floor is zero, the way the mint refuses minimums of zero, unless the caller says `acceptAnyAmount` out loud; `collectFloor` in `packages/nextjs/lib/hedera/__live__/positionRun.ts` is where the signed run sources it — what the manager owes the position, the same tolerance under it as the mint's minimums. `explainError` in `packages/nextjs/lib/hedera/failure.ts` names the 184 when one of the other two patterns is tried anyway, reading it out of the mirror node's `/actions` when the `multicall` erased it. Afterwards the claim is checked rather than assumed: `hbarPaidByCollect` in the same run module adds the sender's own line in the transaction record to the fee it paid and refuses the run unless that is at least what the manager owed the position, so a collect that handed over WHBAR tokens could not be recorded as one that paid HBAR, while anything above it is reported as what the sweep found rather than treated as an error. `checkPositionEvidence` in `packages/nextjs/lib/hedera/evidence.ts` makes the same comparison again, from the mirror node, for anyone reading the record without a key.

**The test that keeps it fixed** — `yarn test:unit`: "rebuilds the split collect, whose three calls are what deliver native HBAR" decodes the calldata of the transaction above and requires the builder to produce the same bytes, and "sends the wrapped HBAR to the manager first, because collecting both sides at once reverts" pins the order. "carries the floor into the unwrap, which is the only guard that call has" and "refuses a floor of zero, because the unwrap sends whatever the manager holds" hold the sweep. "is what the account gained plus the fee it paid, and it equals what the position was owed", "refuses a collect that paid the wrapped token instead: the account gained nothing but the fee" and "names, rather than refuses, wrapped HBAR the unwrap swept out of the manager" hold the guard, and "fails a cycle whose collect paid another amount than the file claims" holds the keyless check. `yarn test:mock` runs the failure against an original position manager and pool injected at their testnet addresses: "reverts TransferFail(184) when a collect sends both sides to the manager, as the Uniswap pattern does", "loses that reason entirely when the same collect is wrapped in a multicall", "delivers native HBAR and the token when the collect is split in three", which also asserts that no wrapped token is left behind, and "refuses the unwrap when the manager holds less wrapped HBAR than the floor the collect names", whose control is the same two calls with no floor succeeding after moving nothing at all.

## A burn the simulators accept, and the network refuses

**Symptom** — closing a position ends with `burn`, and an empty position burns cleanly. Asked to price it, `eth_call` returns without an error and `eth_estimateGas` answers a number, so a wallet shows a fee and sends. The transaction reverts with `HederaFail(292)`, and the gas is charged. Nothing in the simulation, the wallet or the position's own state says what was missing.

**Real cause** — the manager burns a position by moving its NFT back to itself, and an HTS NFT moves only with the owner's approval, which the token service holds below the EVM. `setApprovalForAll` is sent to the NFT's own facade, not to the manager, and the manager reads it with `isApprovedForAll`. Like the allowance of the section on the simulators, that check runs at consensus and not during a simulation, so the only way to know before signing is to read the approval.

Reading `isApprovedForAll` before signing costs nothing, which is the whole of the difference between that cycle and a burn that reverts.

**How the template protects** — `buildBurn` in `packages/nextjs/lib/hedera/position.ts` takes what `isApprovedForAll` answered and refuses to build the call when it is false, naming the approval to send and why no simulator catches it; `readNftApproval` in `packages/nextjs/lib/hedera/positionReads.ts` is the read and `nftApprovalVerdict` in `packages/nextjs/lib/hedera/positionPreflight.ts` the verdict a panel shows, with the action `approve`, while `buildNftApproval` builds the remedy. `packages/nextjs/lib/hedera/__live__/positions.signed.ts` is that sequence run end to end: it asks `checkPositionBurn` first, sends the approval when the answer is `fail`, asks again, and `assertPreflightPasses` stops the run rather than send a burn the network would refuse.

**The test that keeps it fixed** — `yarn test:unit`: "rebuilds the burn, and refuses to build one while the manager holds no approval" checks both halves against the calldata of the transaction above, and "refuses to start, naming every failing check and its action" holds the guard that stops the signed run. "reads the answer from the NFT facade, and reports whichever answer came back" is what keeps the read honest: it replays a captured `isApprovedForAll` of each kind — this project's account, which granted it, and a third party that holds positions and granted nothing — so a check that stopped reading the chain and always answered `pass` fails there rather than on chain, where it would send the first transaction of the table above again. "refuses a burn that left the position behind" and "fails a cycle that left the position on the account" are the other end of it: the serial has to be gone from the manager and from the account before a cycle may be recorded as closed. `yarn test:mock`: "reverts HederaFail(292) on a burn while the manager holds no approval on the position NFT" and "burns the position once the manager is approved, and the serial is gone" reproduce the refusal and its remedy offline.
